# Keep generated names, soften no-recovery, fix lockout

**Bottom line: the research supports the owner's one-link-one-account rule and the 1,000-seat cap, modifies the "choose your own password" idea, and argues against free-text usernames and a literal "lost means gone" policy.** Learners should not type a free-text username, because a child's typed name cannot be screened for real names and FR-035 forbids storing them. The server should offer five generated names to pick from, or keep the current generated Beta ID. A chosen password should be an opt-in path for older learners. The default for everyone should be a generated passphrase, because no source supports child-chosen text passwords and the small studies found favour generated, picture or word-based secrets for ages 4-12. "No self-service reset, no email, nothing recoverable" is workable only if an admin can still issue a reset, which the spec already allows in FR-010. That reset should be a single-use link rather than a password an admin can see, and a one-time recovery code should be added. The most urgent fix is neither username nor password. The lockout rule in FR-013 (10 failures per 15 minutes per address) will lock out a whole classroom behind one school network address and conflicts with SC-004. The 200,000-iteration PBKDF2 setting is a third of OWASP's current figure. The file-backed store on Cloud Run can silently break both the cap and uniqueness unless the service is pinned to one instance with durable storage. Legal points on children's data (India's DPDP Act, COPPA, GDPR/UK) rest on secondary sources and need counsel before the beta widens.

**How to read the evidence.** Each note's author could not reach several primary sources: Code.org, Seesaw, Khan Academy, ICO, MeitY and Federal Register pages returned 403 or similar. I mark claims as **Sourced** (a fetched page, URL cited), **Secondary** (seen via search snippet or law-firm summary) or **Inference** (the researchers' or my reasoning). Confidence is High, Medium or Low. I read `spec.md` and the task list by keyword search only. I did not read `plan.md`, `data-model.md` or `contracts/http-api.md`, so those files are listed as needing review rather than mapped.

## The one-link-one-account rule and the cap are sound, but their edges leak

The rule that one link creates exactly one account, with seats equal to accounts plus unused unexpired invites, is already in FR-003 and FR-006 and matches best practice. Tokens of 256 bits from a CSPRNG, stored only as a hash, exceed every guidance document found ([OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), which asks for at least 64 bits and suggests 128). Activation by a button that sends a POST, never on page load, is the right defence against link previews and mail scanners that fetch URLs before a person clicks. Vendors report scanners burning one-time tokens ([Supabase auth issue](https://www.github.com/supabase/auth/issues/1214); [Slack's unfurler](https://api.slack.com/robots)), and OWASP notes that SameSite=Lax cookies still travel on GET navigations ([OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html)). Confidence: High for token design and POST activation (Sourced); Medium for scanner behaviour, which comes from vendor and issue-tracker reports and not Microsoft or WhatsApp documentation.

The weak points are the ones the proposal creates. First, a forwarded or projected link is a bearer secret, and "whoever opens it first gets the account" (the spec's own edge case) is more damaging once the claimant also picks the username and password. The researchers' mitigations, all **Inference** built on the W3C capability-URL draft ([W3C](https://www.w3.org/TR/capability-urls/)), are to place the token in the URL fragment (`/join#token`) so it never reaches Cloud Run request logs or Referer headers, to send `Referrer-Policy: no-referrer` and `Cache-Control: no-store`, and to require a short code handed over separately, with about five wrong tries killing the invite. Second, letting a person choose a name creates a "name already taken" oracle. OWASP's registration guidance treats "this user ID is already in use" as the incorrect example ([OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)). That leak is small here, since only invite holders can probe it, but offering the server's own suggestions removes it altogether. Third, the cap is only as safe as the storage under it. Cloud Run instances serve concurrent requests, have an ephemeral in-memory filesystem and scale to zero ([Cloud Run contract](https://docs.cloud.google.com/run/docs/container-contract)), so a file store survives only with a maximum of one instance and a durable volume (the volume part is unverified for this deployment). Under Postgres, counting rows at the default isolation levels lets two transactions both see room ([PostgreSQL docs](https://www.postgresql.org/docs/current/transaction-iso.html)), so the later managed store needs a unique key and a transactional counter. SC-005's test of 50 simultaneous activations for 10 seats is the right test and should also run against whatever store replaces the file.

A refinement from the researchers: because consuming an invite turns one invite seat into one account seat, activation never needs a cap check. The check belongs at invite creation, inside the same lock (Inference, High confidence on the logic). Add per-label quotas, 80% and 95% cap alerts, and a generic "link no longer valid" message that does not reveal whether a link was used, expired or revoked.

## Generated names beat free text, and generated secrets beat child-chosen ones

**Usernames.** Free text is the one place where the owner's idea collides with FR-035. Children's services handle this with generation or review, not detection. Khan Academy strongly encourages child accounts not to use real names, and for under-13s the parent sets the username (Secondary, [Khan Academy support](https://support.khanacademy.org/hc/en-us/articles/216368447-What-are-the-basic-requirements-for-usernames), page returned 403). ChessKid assigns computer-generated usernames and has staff approve custom ones ([ChessKid](https://support.chesskid.com/article/4816-usernames-and-custom-usernames)). The ICO's children's code guidance reportedly cites system-generated usernames as protective (Secondary, [ICO](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/childrens-information/childrens-code-guidance-and-resources/how-to-use-our-guidance-for-standard-one-best-interests-of-the-child/best-interests-framework/data-sharing-between-users/), 403). No peer-reviewed or regulator evidence shows generated names are safer than free text, and the researchers say so, so this rests on product practice. The reasoning is strong though: names, school names and phone numbers cannot be reliably detected in free text (`jsmith2014`, `mrsjonesclass` pass any pattern filter), and word-list profanity filters fail through obfuscation and the Scunthorpe problem ([Scunthorpe problem](https://en.wikipedia.org/wiki/Scunthorpe_problem)). Recommended policy, which is Inference at Medium-High confidence: the server generates adjective-animal-style names from hand-reviewed lists of about 200 words each, with digits drawn from 2-9 so there is no 0/1/O/l confusion, shows five options with a reroll button, and reserves the chosen one against the invite for a few minutes. It uses lowercase ASCII only, which sidesteps normalisation and confusable-character problems that RFC 8265 and Unicode TR39 exist to manage ([RFC 8265](https://www.rfc-editor.org/rfc/rfc8265.html); [UTS #39](https://unicode.org/reports/tr39/)). It has no availability-check endpoint and reserves names such as admin, teacher and the product name. If the owner still wants free text, the fallback is a canonical lowercase allowlist, a reserved-name list, a leetspeak-folded denylist with a false-positive allowlist, a reject-never-clean rule, and an admin "rename or disable" action. That fallback is a weaker compromise of FR-035, not a fix. A real design choice remains: the current `BETA-7KQ3-M9XP` is secure but hard for an 8-year-old to type, so a friendlier generated format is a usability improvement, not a security one. Generated names are guessable if the word lists are public, so treat the username as non-secret and rely on the password and throttling.

**Passwords.** Everything found points the same way for young children. Code.org suggests picture passwords for roughly ages 4-8 and secret words for 9-12, generated by the platform and reset by teachers (Secondary, [Code.org](https://support.code.org/hc/en-us/articles/22047054952973), 403). Small studies find children remember picture-based secrets better than alphanumeric ones ([KidsPic, 40 children aged 6-11](https://experts.boisestate.edu/en/publications/pictures-are-easier-to-remember-than-spellings-designing-and-eval/); [KidzPass, ages 4-7](https://publikationen.bibliothek.kit.edu/1000144473); [PassTiles](https://arxiv.org/abs/1610.09743)). All are lab-scale and Western, with nothing on India, multilingual or low-literacy settings. Meanwhile NIST SP 800-63B-4 requires at least 15 characters for a single-factor password, a blocklist check, no composition rules, and 64 or more characters allowed ([NIST](https://pages.nist.gov/800-63-4/sp800-63b.html)). No source tells us how to meet that for eight-year-olds, and a 15-character child-chosen password is not realistic. Because the app cannot know a learner's age (no DOB under FR-035), it cannot offer different rules by age. My recommendation, an Inference at Medium confidence: keep the generated passphrase as the default for all learners (the current 4 words from a 256-word list plus 3 digits is, by my arithmetic, about 42 bits, sensible for rate-limited online guessing and not offline cracking), and add a "choose my own instead" link for older learners. That path enforces at least 8 characters (counted after NFC normalisation and trimming), allows up to 128, applies no composition rules, and checks an embedded list of the 100,000 most common passwords plus a kid-specific and context list (username, app name, colours, animals, game names). The embedded list is roughly 1 MB and keeps checking offline; the licence for redistributing the NCSC/SecLists file is unverified. The deviation from NIST's 15 characters should be written down as a risk-accepted exception (no personal data, low-value account, strict throttling), not left implicit. A strength meter is optional: the evidence says meters matter mostly for important accounts and when they score stringently ([Egelman et al.](https://blues.cs.berkeley.edu/wp-content/uploads/2014/07/p2379-egelman.pdf); [Ur et al., USENIX 2012](https://www.usenix.org/conference/usenixsecurity12/technical-sessions/presentation/ur)), and there is no study with children. The server-side blocklist is the real control.

## A warning alone does not carry the no-recovery decision

Every education platform examined has a human reset path: Code.org and Scratch teachers reset or reveal student credentials, ClassDojo teachers replace lost QR codes or generate temporary passwords, and Seesaw teachers can reset home codes at any time (all Secondary or Sourced from help centres: [Code.org](https://support.code.org/hc/en-us/articles/202447276), [Scratch](https://mitscratch.freshdesk.com/en/support/solutions/articles/4000156813-how-do-i-reset-my-students-passwords-), [ClassDojo](https://help.classdojo.com/hc/en-us/articles/360023367251-How-Students-Can-Login-With-an-Individual-QR-Code), [Seesaw](https://help.seesaw.me/hc/en-us/articles/206447475-How-to-reset-student-passwords)). None relies on "lost equals gone". The researchers found no published data on lockout, abandonment or support load from lost children's passwords, so any claim about how often this will bite is unsupported. The evidence on warnings is thin: most users of an end-to-end-encrypted email service did save recovery codes, with confusion about what the code can restore as the main obstacle ([Höltervennhoff et al., USENIX Security 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/h%C3%B6ltervennhoff)), and 1Password makes people type the code back before setup completes ([1Password Community](https://www.1password.community/1password-at-home-31/improve-the-recovery-code-backup-process-20720)). No study tests warnings with children.

So my position is: **support** "no email and no self-service reset by the learner"; **modify** "cannot be recovered" to "we cannot look it up, but an administrator can give you a new one-time sign-in link, and your progress on this device may be lost"; and **argue against** treating a warning as the safety net. The gap in this product is that admins do not know the learners, unlike a teacher. Three controls follow (all Inference; the first and third are Medium-High confidence, the second Medium). The first is a one-time recovery code shown at activation, hashed at rest, that resets the password only and does not sign in, with a required typed confirmation of part of it (not a checkbox), consistent with NIST's look-up-secret rules ([NIST authenticators](https://pages.nist.gov/800-63-4/sp800-63b/authenticators/)). The second is to change admin reissue (FR-010) from "issue a replacement password" to "issue a single-use, short-expiry reset link", so the admin never sees or chooses the learner's password. The reset is audited, rate-limited per admin, revokes existing sessions, leaves expiry unchanged, and shows the learner a notice at next sign-in. Because a pseudonymous username proves nothing about who is asking, the requester should prove the request through the cohort contact or a batch code received out of band, not by quoting the username. The third is a printable login card holding the username and recovery code but never the password, which fits classrooms as Code.org and ClassDojo do. Reject secret questions and password hints: NIST prohibits them and OWASP warns they are guessable. Also tell learners that progress lives only in the browser, so a new device loses it whatever happens to the password, and make the expiry message distinct from a bad-password message, since a child cannot tell the two apart.

## Lockout, hashing and sessions will fail before the username does

**Lockout.** FR-013 blocks a Beta ID, and separately a network address, after 10 failures in 15 minutes. NIST allows up to 100 consecutive failures per account and endorses increasing delays over hard lockout; OWASP warns that account lockout can be abused for denial of service ([NIST](https://pages.nist.gov/800-63-4/sp800-63b.html); [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)). Two things make the current rule worse than it looks. A school lab shares one public address, so 40 children mistyping a new password will trip a per-address limit of 10, which contradicts SC-004 (a class of 40 signs in within 2 minutes). And any classmate can lock a child out by guessing their name. The researchers propose, as Inference with Medium confidence on the numbers, counting failures per account-and-address pair, applying progressive delay after about 5 free failures (5 s up to 15 min) and not a hard block, keeping a per-address ceiling near 60 failures per 15 minutes that slows and does not block, a hard ceiling of 100 failures per 24 hours per account that requires an admin reset, and a global cap on concurrent hash work. Spraying a few popular passwords across all 1,000 accounts is the main threat with chosen passwords, and per-account limits never see it, which is what the address limit and the common-password blocklist are for. Two operational traps: counters held in process memory are per instance on Cloud Run, so limits multiply with autoscaling unless counters live in the store or the service is pinned to one instance; and the client address must be read from the correct position of `X-Forwarded-For`. Google's load balancer appends its values to whatever the client sent, so the leftmost entry is forgeable ([GCP load balancing](https://docs.cloud.google.com/load-balancing/docs/https)). Which entry to trust for direct `*.run.app` traffic was not verified and should be tested with a forged header.

**Hashing.** T005 specifies PBKDF2-HMAC-SHA256 at 200,000 iterations. OWASP's current minimum is 600,000 for that function, or Argon2id at 19 MiB, t=2, p=1 ([OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html)). Go 1.24 added a standard-library `crypto/pbkdf2` ([Go 1.24 notes](https://go.dev/doc/go1.24)), which Go 1.23 lacks. The researchers' benchmark (a laptop, so Low confidence for Cloud Run) put 200,000 iterations at about 143 ms and 600,000 at about 404 ms. Cloud Run limits CPU below 1 vCPU to concurrency 1 ([Cloud Run CPU](https://docs.cloud.google.com/run/docs/configuring/cpu)), so 40 near-simultaneous sign-ins could take many seconds at 600,000. The practical advice is to upgrade Go, use at least 1 vCPU, keep a version tag in the stored hash so parameters can be raised on next login (T005 already reads the iteration count from the string), bound concurrent hashing, throttle before hashing, and still run a dummy hash for unknown users. If the owner keeps 200,000 on a tiny instance, record that as a documented exception. This matters more with chosen passwords, because a leaked hash file is then attackable with human-pattern guesses, while 42-bit generated passphrases resist better.

**Sessions.** Fourteen-day sessions (FR-012) are long for school machines. OWASP suggests 15-30 minute idle timeouts for low-risk apps ([OWASP Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)). Add a "shared computer" choice with a short session and an idle timeout, keep 14 days for a home device, and keep the existing "sign out and clear progress" dialog (T036). Browsers cannot be reliably stopped from offering to save a password, so server-side session limits are the real control ([W3C thread](https://lists.w3.org/Archives/Public/public-webapps/2013OctDec/1070.html), a 2013 browser-developer statement, Low confidence on current behaviour).

## Risks that remain

The legal picture is the largest unresolved item, and every point below needs counsel because it rests on secondary sources. **India (DPDP Act and Rules).** Anyone under 18 is a child, and section 9 as summarised requires verifiable parental consent and bans tracking, behavioural monitoring and targeted advertising of children, with children-related duties commencing about 18 months after the Rules were notified in November 2025, around May 2027 (Secondary: [SCC Online](https://www.scconline.com/blog/post/2025/12/26/digital-personal-data-protection-rules-2025-key-highlights/); [dpdpa.com s.9, unofficial](https://dpdpa.com/dpdpa2023/chapter-2/section9.html)). The notification date differs by source (13 or 14 November), and a floated acceleration was not confirmed as notified. The schools' exemption is narrow and attaches to the educational institution, so whether a third-party app operator can rely on it is unsettled. A no-personal-data design may not remove the consent duty if a username plus a label counts as personal data (Inference, Low-Medium confidence), and the cheapest route the researcher identified is the school as the fiduciary with the operator as processor under a written agreement. **US (COPPA).** A username counts only where it works like online contact information, and persistent identifiers such as IP addresses are personal information unless used solely for internal operations ([eCFR 312.2](https://www.ecfr.gov/api/renderer/v1/content/enhanced/current/title-16?part=312&section=312.2); [FTC FAQ](https://www.ftc.gov/business-guidance/resources/complying-coppa-frequently-asked-questions)). This is Sourced for the text, and the conclusion that a username-plus-password account probably needs no verifiable parental consent is Inference. The app will almost certainly be "directed to children", so age screening does not help, and data minimisation is the strategy. The 2025 amendments added written security, retention and disclosure duties with a compliance date of 22 April 2026 (Secondary: [Lowenstein Sandler](https://www.lowenstein.com/news-insights/publications/client-alerts/ftc-finalizes-updates-to-coppa-rule-what-you-need-to-know)), and US exposure is low unless US schools are invited. **EU and UK.** Pseudonymous data is still personal data, and exposure is low for an India-only beta but real if any EU or UK school or family is invited ([GDPR Art. 8](https://gdpr-info.eu/art-8-gdpr/); UK Children's Code scope per [Mondaq](https://www.mondaq.com/uk/privacy-protection/1109232/online-safety-the-icos-childrens-code), 2020-21 sources).

Three concrete conflicts need a decision. FR-038 keeps logs for 30 days, but CERT-In's 2022 directions reportedly require 180 days of ICT logs held in India, and DPDP Rule 8 as summarised mentions one-year log retention; whether either applies to this operator is unresolved ([Nishith Desai](https://nishithdesai.com/research-and-articles/hotline/technology-law-analysis/cert-in-releases-faqs-explaining-the-direction-on-cybersecurity-6139); [SCC Online](https://www.scconline.com/blog/post/2025/12/26/digital-personal-data-protection-rules-2025-key-highlights/)). The feedback form is the main source of accidentally collected personal data, because children can type names and family details, and scrubbing is partial. And the spec's "no personal data" claim should be worded "we do not ask for" and not "we hold none", because usernames, IP addresses in the lockout window and free-text feedback can contain it. Residual security risks the redesign does not remove: a leaked or projected card or invite link, because first-come-first-served stays inherent; admin social engineering, because a pseudonymous username proves nothing about who is asking; a lost recovery code plus a lost password with no reachable admin, which ends in a fresh invite and an orphaned username; and progress held only in browser storage, which leaks between children on shared machines and vanishes on a new device. Passkeys, Argon2id (which needs `golang.org/x/crypto` and breaks the standard-library-only rule, and at 19 MiB per hash strains a small instance) and a teacher role were assessed and deferred, not ruled out.

## Conclusion

The owner's proposal bundles two separate ideas that the evidence treats differently. Binding one invite to one account under a hard cap is well supported and already in the spec. Moving credential creation to the learner is where the design risk sits, because it moves secret and identifier creation, the two things a children's service most wants to control, from the server to the user. The lowest-risk reading keeps the server in charge of the identifier and the default secret, and gives the learner a choice from curated options. That still delivers what the owner probably wants: a name the learner picked and a credential they can opt to change.

The research also moves attention away from the headline questions. The designs that most threaten a 1,000-account classroom beta are the shared-address lockout, the 200,000-iteration hash and the Cloud Run storage assumptions, none of which depend on whether the username is free text. Fix those first, ship the admin reset link and recovery code so "no recovery" does not become "no way back", and take the DPDP and log-retention questions to counsel before the DPDP children's provisions are expected to commence, around May 2027.
